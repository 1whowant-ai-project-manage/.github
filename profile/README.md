# 1whowant-ai-project-manage

AI 项目管理组织（AI Project Management）—— 供多个 AI Agent 与人类协作管理项目、跟踪进度。

> **本页 = 规范权威（单一起点）**：与本组织协作只需读本页，**无需 clone 任何仓库、无需额外授权**。
> 规范与其他文档冲突时以本页为准；本页随规范演进同步更新。

## 🎯 主项目入口

- **主看板**：[AI PM](https://github.com/orgs/1whowant-ai-project-manage/projects/1)
- **项目中枢**：[ai-pm-hub](https://github.com/1whowant-ai-project-manage/ai-pm-hub)（私有，存放组织级记录；**只读引用，不要 clone**）

## 🤖 Agent 上岗流程

1. **读本页**：硬约束全文即下方第 1~6 节，读完再动手；
2. **确认 token**：必须是本组织**细粒度 token**（组织内 `All repositories` + `Organization Projects` 读写）；
3. **认领任务**：`self-assign` ＋ 评论 `claim: <agent-id> @ <UTC 时间>`，两条缺一不可；
4. **建议**：按第 7 节给自己设定巡检与心跳调度（时间与频率可依自身额度、负载调整）。

## 1. 权限边界（最高优先级，不可覆盖）

- ✅ **允许**：本组织内全部仓库、Issue、Project、文件的读写操作；
- ❌ **严禁**：以任何方式访问、读取、写入 `1whowant` 的**个人**仓库与个人 Projects；
  - 组织级 token 对个人仓库天然返回 `403`；若发现任何请求绕过这条边界 → **立即停止全部操作**并新建 issue 报告。
- 🔑 **Token 存放**：只允许放在执行方的**本机私密环境文件**（如 `~/.hermes/.env`，权限 `600`，且该文件不进任何仓库）；
  - **禁止**写进 issue、评论、日志、代码或本组织任何仓库/文件；
  - 跨机交接时**只传口令，不传 token**。

## 2. 仓库定位与内容规范

- 本组织用途：**指导、项目管理（PM）、进度跟踪、任务编排**。它不是代码仓库，不是文件柜。
- ❌ **不要存储**：
  - 代码本体、构建产物、运行日志；
  - 过大的方案文档、中间草稿、二进制附件。
- **产物外置原则**：实际产出（代码、报告、数据）放在各自的外部位置，在 issue 中只记录：**路径、摘要、校验和（SHA-256）、状态、链接**。
- 体量约束：单个文件建议 `< 50KB`；超限就拆分或外置，issue 里放指针。

## 3. 多 Agent 协作模型

### 3.1 可并行共建（不同 Agent 同时做，无需协调）

- Project 看板的视图、字段、自动化配置；
- **不同文件 / 不同章节**的文档；
- **不同 issue** 的处理与推进；
- 标签、里程碑等元数据的维护。

### 3.2 原子单元：同一时刻只能一个 Agent 独占

- **一个 issue / task = 一个原子单元**：同一时间只允许一个 Agent 认领处理，避免编辑冲突；
- **子任务（sub-issue）是更小的原子单元**：把大任务拆成子任务后，不同 Agent 可各领一个并行推进 —— 即「**单元内串行、单元间并发**」；
- sub-project（独立 Project 或里程碑）层面：允许多 Agent 各自推进其下的 issue，互不干扰。

### 3.3 认领协议（所有原子单元通用）

1. **认领前**：检查 issue 的 assignee 与时间线，确认无人认领、或原认领者的进展已明确停滞（**超过 48h 无更新**视为可接管，接管时必须留评论说明）；
2. **认领动作**：`self-assign` ＋ 发表评论 `claim: <agent-id> @ <UTC 时间>`。两条动作缺一不可；
3. **工作中**：关键节点在 issue 评论进度；预计超过 24 小时的任务要说明计划；
4. **完成**：更新 `Status`，评论中给出成果链接与摘要，然后关闭或转入 review；
5. **冲突处理**：发现任务已被他人认领 → **立即让位**，去领下一个任务。不争论、不覆盖、不删除别人的标记。

### 3.4 编辑纪律

- 同一 issue 的**正文编辑**是串行资源：先读后写，最小化改动；
- **追加评论优于改写**他人内容；不静默覆盖别人的状态、字段或记录；
- 发现状态冲突：保留双方证据，新建 issue 提请人类裁决，不要自行「修复」。

## 4. 本地产物协议

### 4.1 产物分三类

| 类别 | 内容 | 处理方式 |
|---|---|---|
| **A · 可入库** | 规格、决策记录、最终文档（`< 50KB`） | 提交到组织内仓库，issue 记**仓库相对路径** |
| **B · 留本地** | 数据集、日志、构建物、大文件、含敏感信息 | **不入库**，issue 记**本地产物指针**（见 4.2） |
| **C · 运行态** | 临时缓存、中间产物 | 不记录 |

### 4.2 本地产物指针（写在 issue 评论，字段固定）

```yaml
artifact:
  host: <执行机器名>
  path: <绝对路径，文件或目录>
  sha256: <文件哈希，或目录清单哈希>
  size: <如 12.3MB>
  created: <ISO8601 UTC>
  access: local-only | org-repo | external-url
  ttl: <保留到哪天>
  reproduce: <可复现时必填：生成命令>
```

### 4.3 取用规则

- **同机**：直接按 `path` 读（需同用户权限）；
- **跨机**：**不得依赖本地路径** → 二选一：① 上传组织内仓库 / Release 附件；② 给出 `reproduce` 命令，由对端重跑；
- **可复现优先**：能由脚本重跑生成的产物，**只记命令 + 依赖版本**，不记路径 —— 最省事也最可靠；
- **本地归口**：`<本机工作根>/<org>/<issue#>/`，用 issue 号反查；按 `ttl` 清理，过期须在 issue 标注；
- **认领人责任**：产物在认领期内由认领人保证可取；交接时必须留 `artifact:` 评论。

## 5. 状态与审批约定

- 任务状态用 Project 的 `Status` 字段：`Todo → In Progress → Done`；
- 需要人工决策的事项：贴 `awaiting-approval` 标签并评论说明选项，然后等待；
- **Agent 永远不得自行标记「已批准」** —— 批准只能由人类账号执行。

## 6. 沟通与可审计性

- 每次实质操作后，在对应 issue 留一条记录：做了什么、结果如何、产物在哪；
- 规范未覆盖的情况：**不要自作主张**，在 issue 中描述问题并等待人类回复；
- 报告失败与报告成功同样重要：**掩盖失败是最严重的违规**。

## 7. Agent 自有调度建议（心跳与巡检）

> 以下均为**建议**：各 Agent 可依自身时区、模型额度、任务负载自行取舍；但**巡检一律只读**，写操作必须先取得人类授权。

建议每个接入本组织的 Agent 在**自己的运行环境内**（不放进本组织仓库）设置两类调度：

### 7.1 变化唤醒巡检

- 定期**只读**扫描本组织 Issues / Projects；
- **仅在看板有变化时**才唤醒 LLM 产出简报，无变化则静默跳过 —— 避免无变化时空烧 token 与额度；
- 推荐做法：先跑一个**确定性的看板指纹**（不含时间戳等易变字段）与上一轮逐字节比对，一致即跳过。

### 7.2 心跳

- 作用：证明 Agent 在线，给人类一个可预期的状态节拍；
- **时间建议**：白天 `07:00–23:00` 区间内**每 4 小时一次，从 `07:00` 起** —— 即 `07:00 / 11:00 / 15:00 / 19:00 / 23:00`（本地时区）；
- **内容建议**：`≤ 3` 行 —— ① 在线 ② 看板计数 ③ 自上轮以来是否有变化；
- 与巡检的区别：心跳**不论有无变化都发**，巡检**只在变化时发**。

### 7.3 巡检间隔

- 建议在 `20–40` 分钟之间**自适应**，依据：
  1. **本组织任务与项目状况**：open issue 数、是否有 `In Progress`、是否有 `awaiting-approval`、距上次变化多久；
  2. **Agent 所用模型的 rate limit 与 quota**：额度紧张就放长，宽松可缩短；
- 无自适应能力时取中间值 **`30` 分钟**；
- 额度耗尽或触发限流时**必须自动退避**，不得重试轰炸。
